## The four states

**Done — 49% (18 of 37 packages).** This counts packages whose code is
merged to `main` and has passed the full landing checklist run by the
integration-lead session itself (not taken on the word of whoever wrote the
code): the whole module builds and its tests pass together, a data-race
detector runs clean, and a "mutation check" — deliberately breaking the
package's key safety rule, confirming a specific test catches the breakage,
then restoring the code exactly — passes. Landed since yesterday's report:
scheduling (when queued work wakes up and who is responsible for it),
connections (how the product talks to external systems), messaging
(conversations and mailboxes between the product and users, plus policy
over what may be disclosed), accounting (spend tracking, reservations, and
budget limits), effects (the state machine that tracks a real-world action
from proposal to completion), and execution (the state machine that runs
and verifies individual work attempts, including recovering from crashes
mid-attempt). Two of those landings caught and fixed real bugs during the
gate itself, not before it: the execution landing fixed a case where a
timed-out lock (a "lease") could permanently deadlock a task, and fixed the
retry counter so it counts prior attempts instead of assuming there had
only ever been one; the effects landing found and fixed a hole in test
coverage on a rule that stops one organization from reading another
organization's data.

## Glossary for this report

- **Package**: one self-contained unit of Go code owning one part of the
  product (for example, messaging or scheduling); the whole plan is broken
  into 37 of these.
- **Wave**: one batch of packages worked on together; the current batch is
  "wave 2."
- **Lane**: one independent stream of work — in this project, one package
  being implemented by one dispatched process.
- **Worktree**: an isolated copy of the repository where one package's work
  happens without disturbing `main`.
- **`main`**: the shared, always-releasable line of code every finished
  package eventually merges into.
- **Landing gate**: the integration-lead session's checklist (build, test,
  race check, mutation check) a package must pass before it can merge.
- **Mutation check**: deliberately breaking a package's key safety rule,
  confirming a specific test catches the breakage, then restoring the code
  exactly — proof the test would actually catch a real regression.
- **Integration-lead session**: the Claude Code session (this one, named
  `zatiti`) responsible for merging finished packages into `main` and
  running the landing gate.
- **Claim**: a lock one session takes on a shared file or task so another
  session doesn't duplicate or collide with the work.
- **kazi**: the tool that automatically grinds on a task until its
  automated checks pass; `kazi status` reporting "no LIVE runs" means
  nothing is currently running under it.
- **AGENTS.md**: the committed, self-contained specification file inside
  each package's folder that tells an implementing agent its mission, file
  ownership, interfaces, and acceptance criteria, so it never needs the
  full RFC (the original design document) to do its job.
- **MCP (Model Context Protocol)**: the standard protocol that lets an AI
  coding assistant call into another program's features; Zatiti's `mcp`
  package is the adapter that exposes Zatiti this way.
