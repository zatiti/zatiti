confirmed already-satisfied with no code change needed). This covers three

- The second-largest batch ("wave 3," 15 cards, all landed): every domain

- **Wave 4, the actual worker loop's start (6 cards, all landed today):**
  this is the headline. The centerpiece is the durable "worker turn"
  pipeline — the record of one worker's ongoing decision stream, whether
  triggered by an incoming chat message, an assigned task, or a standing
  responsibility, admitted exactly once per trigger and safe against being
  duplicated by a retry. Alongside it: automatic claiming of hosted work (a
  worker doesn't need a human to manually tell it "go" once a task is
  ready), bounded chief conversations before any task exists (so a chief
  can ask a clarifying question or propose configuration without needing a
  task to already exist), typed reasons for why a worker is waiting
  (missing setup, waiting on a person, waiting on budget, and so on) with
  real re-checking on wake rather than blindly resuming, and a controller
  restart correctly picking back up without losing a worker's cumulative
  spend. This one received the most careful review of anything landed
  today: every new operation's schema was diffed byte-for-byte against the
  frozen contract (not eyeballed), the three required tests were read in
  full to confirm they test real behavior rather than a fake stand-in, and
  the whole module's test suite was run and compared against the
  pre-existing baseline twice to prove nothing else broke. The other five
  cards in this wave closed out worker-proposal authorization (with the
  same route every other operation uses, not a new privileged path),
  correlating a human review decision back to the worker turn that's

  tests proving the network transport correctly restarts.

## Glossary for this report

- **Card**: one numbered unit of remediation work ("P00" through "P49"),
  each scoped to roughly one code package.
- **Wave**: a batch of cards grouped by dependency order — cards in the
  same wave can run in parallel; a later wave's cards depend on an
  earlier wave's cards being done.
- **Milestone (M0-M4)**: a marker of real product capability (e.g. "a
  chief can do useful work"), spanning multiple waves — the thing that
  actually matters, as opposed to a wave, which is just a scheduling
  grouping.
- **This session / lead**: the Claude Code session (name "zatiti" in
  this repo) coordinating the whole effort — claiming cards, dispatching
  background workers to implement them, and landing the result.
- **Worker / lane** (in this report's fleet sense): one background AI
  session doing the actual coding for a single card, in its own isolated
  copy of the repo. (Not to be confused with a "worker" in the product's
  own vocabulary — the AI agent the product itself dispatches to do work,
  which is what this plan's cards are actually building support for.)
- **Claim**: a lock a session takes on one card (or a shared resource,
  like the build lock) so two workers don't duplicate the same work.
- **Landing / land**: committing a card's finished work to the shared
  main branch after it passes its checks.
- **Tracked-red / expected-red list**: a maintained list of packages
  that are known to fail their tests for an already-understood, already-
  assigned-to-a-card reason — so a new failure that isn't on the list is
  treated as a real problem, while a listed one doesn't block other
  work from landing.
- **Build lock**: a machine-wide lock meant to ensure only one expensive
  full-test-suite run happens at a time on the shared build machine.
